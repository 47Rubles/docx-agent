# Секреты и конфигурация

Ключ API в этом проекте **никогда не лежит в репозитории**. Он живёт в
переменной окружения, а в конфиге — только плейсхолдер, который подставляется
в памяти в момент загрузки.

## Схема в одну строку

```text
        локально                              в CI
┌───────────────────────┐          ┌──────────────────────────────┐
│ Переменная уровня     │          │ GitHub Actions Secret        │
│ User: LLM_API_KEY     │          │ LLM_API_KEY                  │
│ (ставит скрипт)       │          │ (Settings → Secrets)         │
└───────────┬───────────┘          └──────────────┬───────────────┘
            │                                     │
            └────────► config/settings.yaml ◄────┘
                         api_key: "${LLM_API_KEY}"
                                  │
                                  ▼
                    подстановка в памяти при загрузке
                    (результат никуда не пишется)
```

## Локально

Задать ключ один раз:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\set-api-key.ps1
```

Скрипт спросит ключ с маскировкой (`Read-Host -AsSecureString`), проверит его
запросом к провайдеру и запишет в **пользовательскую** переменную окружения
`LLM_API_KEY`. В файлы, в репозиторий и в чат ключ не попадает.

Проверить, что ключ виден текущему процессу и связь работает:

```powershell
python scripts\smoke_test.py
```

Альтернатива — файл `.env` рядом с проектом (он в `.gitignore`):

```powershell
copy .env.example .env
```

Файл `.env` читается через `python-dotenv` и имеет **низший** приоритет:
реальное окружение всегда важнее файла. Шаблон `.env.example` лежит в
репозитории и содержит только имена переменных.

## В CI

Тот же ключ добавляется в репозитории на GitHub:

```text
Settings репозитория → Secrets and variables → Actions → New repository secret
  Name: LLM_API_KEY
  Value: <тот же ключ>
```

Workflow `.github/workflows/ci.yml` подставляет его в окружение шага:

```yaml
env:
  LLM_API_KEY: ${{ secrets.LLM_API_KEY }}
```

Секреты из `Settings → Secrets and variables` не маскируются в логах GitHub
автоматически, поэтому в проекте два предохранителя:

* `scripts/smoke_test.py` печатает только факт ответа, а текст ошибок чистит
  через `mask_secrets()`;
* `scripts/check_secrets.py` перед сборкой ищет в отслеживаемых файлах
  характерные префиксы ключей (`ghp_`, `AIza`, `AQ.Ab`, `sk-`, `AKIA`, блоки
  приватных ключей) и валит сборку, если что-то нашлось.

Секреты не попадают в сборки pull request из форков — там шаг smoke-теста
просто пропускается.

## Как это работает в коде

`config/settings.yaml` хранит плейсхолдер:

```yaml
llm:
  api_key: "${LLM_API_KEY}"
```

`src/core/settings.py` при загрузке конфигурации подставляет значение
переменной окружения. Ничего не пишет на диск, в лог ключ не попадает:

* если переменной нет — бросается `SecretNotConfigured`, в тексте исключения
  только **имена** переменных, никогда значения;
* `api_key_fallbacks` внутри секции `llm` задаёт резервные источники ключа
  (для Gemini — `GEMINI_API_KEY`), чтобы можно было переиспользовать уже
  настроенный ключ из другого проекта. Список живёт внутри профиля
  провайдера, поэтому при переключении меняется вместе с ним;
* `mask_secrets()` прячет значение в тексте ошибки перед выводом в лог.

## Смена провайдера (например, на Groq)

Способ хранения ключа от провайдера не зависит — меняется только профиль в
конфиге и способ передачи ключа.

1. В `config/settings.yaml` закомментируй секцию `llm` и раскомментируй
   готовый блок `llm` для Groq внизу файла.
2. Запусти `scripts\set-api-key.ps1` и вставь Groq-ключ. Скрипт сам читает
   конфиг и поймёт, что ключ надо передавать как `Authorization: Bearer`,
   а не заголовком `x-goog-api-key`.
3. Проверь: `python scripts\smoke_test.py`.

Особенности Groq, уже учтённые в конфиге:

* ключ имеет префикс `gsk_` и передаётся в `Authorization: Bearer`;
* с машины без прокси Groq отдаёт 403 (гео-блок) — скрипт настройки и
  smoke-тест ходят через прокси `HTTPS_PROXY`;
* в GitHub Actions прокси не нужен: раннеры не под гео-блоком.

## Особенность Google Gemini

Ключи формата `AQ.*` (Authorization key) принимаются только нативным
эндпоинтом `generativelanguage.googleapis.com` и только заголовком
`x-goog-api-key`. Передача того же ключа в `Authorization: Bearer` даёт 401.
Поэтому в `config/settings.yaml` для Gemini задано:

```yaml
auth_style: header
auth_header: x-goog-api-key
```

## Если ключ всё-таки утёк

Ключ, попавший в git, считается скомпрометированным, даже если его удалили
из следующего коммита: он остаётся в истории.

1. Отозвать ключ у провайдера и выпустить новый.
2. Обновить секрет в GitHub (`Settings → Secrets and variables → Actions`) и
   локальную переменную (`scripts\set-api-key.ps1`).
3. Очистить историю, если репозиторий уже публичный и ключ в нём засветился.

## Перед пушем

```powershell
python scripts\check_secrets.py
```

Скрипт вернёт код 1, если в отслеживаемых файлах найдены похожие на ключи
строки или если `.env` попал в индекс.
