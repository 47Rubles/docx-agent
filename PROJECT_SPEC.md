# Техническая спецификация: Автономный агент генерации и версионирования документов DOCX (DocxGen Agent)

---

## 1. Общие сведения и назначение системы

**DocxGen Agent** — программный комплекс для сквозной автоматизированной трансформации неструктурированных текстовых требований (технических заданий, регламентов, концепций) в валидные, профессионально сверстанные документы формата Microsoft Word (`.docx`).

Архитектура системы исключает прямую генерацию сырого бинарного файла языковой моделью. Процесс разделен на:
1. **Когнитивный контур:** декомпозиция требований, диалоговое устранение неопределенностей, синтез контента в абстрактное синтаксическое дерево (Document AST).
2. **Детерминированный компилятор:** трансляция AST в OpenXML с контролем типографики, стилей и структуры файла через OpenXML API.

## 3. Спецификация агентного пайплайна

### 3.1. Агент-Интервьюер (Pre-flight Agent)
* **Входные данные:** произвольный текст пользователя, файлы контекста.
* **Функциональные обязанности:**
  * Анализ текста на полноту по чек-листу атрибутов: целевое назначение документа, целевая аудитория, глубина детализации, жесткие разделы, числовые и расчетные параметры.
  * Формирование списка вопросов при обнаружении критических пробелов (не более 3–5 целевых вопросов за итерацию).
  * Формирование списка некритичных допущений (*Assumptions*), фиксируемых в теле документа.
* **Критерий завершения:** подтверждение пользователем параметров либо достижение достаточного порога полноты данных.

### 3.2. Агент-Архитектор (Document Planner)
* **Входные данные:** консолидированное и очищенное ТЗ.
* **Функциональные обязанности:**
  * Построение иерархического древа документа (до 3 уровней вложенности заголовков).
  * Разметка типов контента внутри каждого подраздела: параграфы, таблицы, врезки, математические формулы.
  * Определение бюджетного лимита токенов и требований к фактуре для каждого блока.
* **Выходные данные:** структурный скелет в формате JSON.

### 3.3. Агенты-Синтезаторы разделов (Section Synthesizers)
* **Функциональные обязанности:**
  * Наполнение блоков фактологическим и нормативным содержимым в соответствии со схемой архитектора.
  * Формирование формул исключительно в синтаксисе LaTeX.
  * Структурирование табличных данных в матричные структуры с типизацией ячеек.
* **Механика изоляции контекста:** каждый раздел генерируется независимо с передачей краткого резюме смежных глав для предотвращения дублирования терминов и расхождений в данных.

### 3.4. Агент версионирования и правок (Diff & Revision Engine)
* **Функциональные обязанности:**
  * Прием точечных правок от пользователя («замени расчет в пункте 2.1», «добавь столбец в таблицу 3»).
  * Генерация дифференциального патча к AST.
  * Формирование разметки рецензирования OpenXML: оборачивание удалений в `<w:del>`, вставок в `<w:ins>` с сохранением авторства и таймстемпа изменения.

## 5. Инженерная реализация компилятора DOCX (Низкоуровневый OpenXML)

Компилятор строится на базе `python-docx` с прямым инжектированием XML-фрагментов через `lxml`.

### 5.1. Работа со стилями и корпоративными шаблонами
* **Базовый слой:** система принимает на вход эталонный файл `.dotx` или `.docx`.
* **Правило изоляции форматирования:** запрещается прямое задание шрифтов, кегля и отступов параграфов в коде. Сборщик назначает элементам только семантические стили из шаблона: `Heading 1`, `Heading 2`, `Normal`, `Table Grid`, `Header`, `Footer`.
* Если передан пустой шаблон, движок программно создает системные стили со стандартными типографическими параметрами (гарнитура Aptos/Calibri, модульная шкала отступов 1.15).

### 5.2. Компиляция формул: LaTeX в OMML
Для получения встроенных векторных формул Microsoft Word используется следующая цепочка преобразования:

$$\text{LaTeX} \xrightarrow[\text{latex2mathml}]{\quad} \text{MathML (XML)} \xrightarrow[\text{XSLT (MML2OMML.XSL)}]{\quad} \text{OMML (Office Open XML Math)}$$

Реализация алгоритма на Python:

```python
from lxml import etree
import latex2mathml.commands

class OMMLConverter:
    def __init__(self, xslt_path: str = "assets/xslt/MML2OMML.XSL"):
        xslt_doc = etree.parse(xslt_path)
        self.transform = etree.XSLT(xslt_doc)

    def convert(self, latex_str: str, display_mode: str = "block") -> etree.Element:
        # 1. LaTeX -> MathML
        mathml_str = latex2mathml.commands.process_latex(latex_str)
        mathml_root = etree.fromstring(mathml_str.encode('utf-8'))
        
        # 2. MathML -> OMML с помощью XSLT трансформации
        omml_root = self.transform(mathml_root).getroot()
        
        # 3. Приведение к блочному или строчному формату Word
        if display_mode == "block":
            omml_para = etree.Element("{http://schemas.openxmlformats.org/officeDocument/2006/math}oMathPara")
            omml_para.append(omml_root)
            return omml_para
        return omml_root
```

### 5.3. Сборка сложных таблиц
Стандартная таблица дополняется структурными свойствами на уровне OpenXML:
1. **Дублирование шапки при переносе:** `<w:trPr><w:tblHeader/></w:trPr>`.
2. **Защита строки от разрыва страницами:** `<w:trPr><w:cantSplit/></w:trPr>`.
3. **Фиксация ширины и автораспределение:** таблица создается с атрибутом `w:tblW w:type="dxa"`. Каждая ячейка получает жестко вычисленную ширину в `dxa` (1 дюйм = 1440 dxa; при рабочей области страницы 9360 dxa ширина вычисляется пропорционально процентам из AST).
4. **Чередование строк (Zebra striping):** к четным строкам данных применяется заливка `<w:tcPr><w:shd w:val="clear" w:color="auto" w:fill="F4F5F7"/></w:tcPr>`.
5. **Объединение (Cell Merging):**
   * Горизонтальное: `<w:gridSpan w:val="N"/>`.
   * Вертикальное: `<w:vMerge w:val="restart"/>` для первой строки, `<w:vMerge/>` для последующих.

### 5.4. Врезки (Callout Boxes)
Реализуются как одноячеечная таблица с кастомными границами:
* **Левая граница:** одинарная линия толщиной 24 (3 pt) с акцентным цветом (Инфо: `#0066CC`, Предупреждение: `#E6A23C`, Ошибка: `#D32F2F`).
* **Остальные границы:** `<w:top w:val="none"/>`, `<w:right w:val="none"/>`, `<w:bottom w:val="none"/>`.
* **Фон:** светлая пастельная подложка ячейки (`#F0F7FF`, `#FEF9E7`, `#FDF2F2`).
* **Внутренние отступы:** установка тега `<w:tcMar>` (верх/низ: 120 dxa, лево/право: 180 dxa).

### 5.5. Оглавление (TOC), нумерация и поля пересчета
* **Блок оглавления:** инжектируется в виде динамического поля Word (TOC \o "1-3" \h \z \u).
* **Принудительное обновление номеров страниц:** в файл `word/settings.xml` инжектируется директива `<w:updateFields w:val="true"/>` для автоматического обновления всех полей при открытии файла в Word.
* **Нумерация «Страница X из Y»:** формируется в нижнем колонтитуле через комбинирование нативных полей `PAGE` и `NUMPAGES`.

### 5.6. Механизм рецензирования (Track Changes)
При активации флага `enable_track_changes`:
* **Вставка нового фрагмента:** оборачивается в `<w:ins w:id="..." w:author="AI Agent" w:date="..."><w:r><w:t>...</w:t></w:r></w:ins>`.
* **Удаление фрагмента:** оборачивается в `<w:del w:id="..." w:author="AI Agent" w:date="..."><w:r><w:delText>...</w:delText></w:r></w:del>`.

## 8. Нефункциональные требования

1. **Скорость генерации:** время компиляции документа объемом до 50 страниц из готового JSON AST не должно превышать 3.5 секунд (без учета сетевых задержек API языковой модели).
2. **Валидность бинарного формата:** итоговый `.docx` обязан проходить строгую валидацию XML-схем ECMA-376 (Office Open XML) без всплывающих предупреждений Word о повреждении структуры или необходимости автовосстановления файла.
3. **Изоляция сбоев:** ошибка компиляции отдельного блока (например, синтаксическая ошибка в LaTeX-формуле) не должна аварийно останавливать сборку всего документа; сбойный блок заменяется на текстовый эквивалент с маркером предупреждения для пользователя.
4. **Безопасность:** отсутствие внешних сетевых вызовов в контуре сборщика OpenXML; изоляция работы с временными файлами через изолированные буферы памяти (`io.BytesIO`).
