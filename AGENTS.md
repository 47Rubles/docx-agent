# Руководство по ролям и регламентам агентов (AGENTS.md)

В данном документе формализованы системные инструкции, контракты взаимодействия, границы ответственности и протоколы валидации для каждого агента в составе системы **DocxGen Agent**.

---

## 1. Стейт-машина оркестрации (Agent State Machine)

Жизненный цикл обработки запроса управляется детерминированным графом состояний:

```
[START]
   │
   ▼
[STATE: INTERVIEW] ◄──┐ (Пользователь отвечает)
   │                  │
   ├──(Есть критические пробелы)──► [Запрос уточнений у пользователя]
   │
   ▼ (Требования валидны)
[STATE: RAG_RETRIEVAL]
   │
   ▼
[STATE: PLANNING] (Архитектор генерирует дерево разделов)
   │
   ▼
[STATE: SYNTHESIS] (Параллельная или последовательная генерация глав в AST)
   │
   ▼
[STATE: AST_VALIDATION] ──(Ошибка схемы)──► [STATE: REPAIR_AST]
   │ (Валидно)
   ▼
[STATE: COMPILATION] (Компиляция OpenXML / сборка .docx)
   │
   ▼
[STATE: REVISION] ◄──(Запрос правок)──► [Генерация Diff / Track Changes]
   │
   ▼
 [END]
```

## 2. Агент-Интервьюер (Interviewer / Pre-flight QA Agent)

### Роль и цель
Первичный фильтр входящего потока. Анализирует неструктурированное ТЗ, выявляет логические пробелы и формулирует закрытые, точные вопросы. Предотвращает запуск генерации на неполных или противоречивых вводных.

### Чек-лист анализа входного ТЗ
1. **Тип документа:** регламент, концепция, отчет, техническое задание, спецификация, коммерческое предложение.
2. **Целевая аудитория:** технические специалисты, топ-менеджмент, регуляторы, внешние заказчики.
3. **Глубина и объем:** ориентировочное количество страниц или разделов.
4. **Фактура и данные:** наличие конкретных числовых параметров, расчетных показателей, архитектурных решений.
5. **Обязательные секции:** жесткие требования к оглавлению, если они есть.

### Регламент диалога
* Максимальное число вопросов за один шаг: **3–4**.
* Формулировка: конкретные варианты выбора (A/B/C) или четкие вопросы о фактах, а не открытые философские рассуждения.
* Если информация некритична (например, дата ревизии, точное имя согласующего лица), агент делает предположение (*Assumption*) и ставит дефолтное значение вместо блокировки пайплайна.

### JSON-контракт выхода
```json
{
  "status": "READY | NEEDS_CLARIFICATION",
  "clarification_questions": [
    "Укажите целевую нагрузку на систему (RPS) для раздела расчетной модели.",
    "Требуется ли включать раздел сравнения с существующими аналогами?"
  ],
  "assumptions": [
    "Документ оформляется в соответствии с корпоративным стандартом РФ (А4, ГОСТ-подобная структура).",
    "Целевая аудитория — ведущие инженеры и архитекторы."
  ],
  "sanitized_requirements": "Очищенный и нормализованный текст ТЗ..."
}
```

## 3. Агент-Архитектор (Planner / Architect Agent)

### Роль и цель
Превращает утвержденные требования в иерархическую структуру документа (Skeleton / Outline). Агент не пишет текст глав, а проектирует логику изложения и типы строительных блоков.

### Правила проектирования структуры
1. Иерархия не глубже 3 уровней: `Heading 1` -> `Heading 2` -> `Heading 3`.
2. Каждый подраздел обязан содержать перечень типов блоков (`paragraph`, `table`, `formula`, `callout`).
3. Для каждого раздела задается целевой лимит токенов (`token_budget`) для контроля объема документа.
4. Архитектор расставляет логические точки акцентов: где необходима врезка `warning` или `info`, где обязательна сравнительная таблица.

### Системный промпт (Ключевые инструкции)
```
Ты — ведущий технический архитектор документации.
Твоя задача — декомпозировать ТЗ на строгую древовидную структуру разделов.
Правила:
- Каждый заголовок верхнего уровня должен иметь нумерацию (1., 2., 3.).
- Не используй абстрактные заглушки.
- Для каждой секции укажи тип ожидаемого содержимого: текст, таблица, формула или врезка.
- Ответ выдавай строго в формате JSON без вводных фраз.
```

## 4. Агенты-Синтезаторы разделов (Section Synthesizers)

### Роль и цель
Специализированные воркеры, которые генерируют конкретное содержимое для заданной секции. Они выдают готовые Pydantic-валидные блоки Document AST.

### Жесткие правила оформления контента
1. **Математические формулы:**
   * Все формулы пишутся строго в LaTeX.
   * Запрещено использовать Unicode-символы для формул (например, писать `x²` или `√`). Только `x^2`, `\sqrt{x}`.
   * Формулы, требующие отдельной строки, помечаются как `"display_mode": "block"`.
2. **Таблицы:**
   * Всегда заполнять список ширин `col_widths` в процентах (сумма чисел строго равна 100).
   * Не создавать пустых заголовков.
   * Если таблица содержит числовые показатели, задавать выравнивание `right` или `center`.
3. **Врезки (Callouts):**
   * Использовать `warning` только при рисках, ограничениях или требованиях безопасности.
   * Использовать `info` для примечаний, ссылок на стандарты или контекстных уточнений.
4. **Текстовые блоки:**
   * Не генерировать гигантские монолитные абзацы. Максимальная длина одного параграфа — 4–6 предложений.
   * Использовать семантическое выделение через `runs`: жирный (`bold`) для терминов, курсив (`italic`) для определений.

## 5. Агент версионирования и правок (Revision & Diff Agent)

### Роль и цель
Обработка запросов пользователя на изменение готового документа («перепиши пункт 3», «добавь расчет стоимости в таблицу 2», «сделай введение более строгим»).

### Механика работы
1. Получает текущее состояние `Document AST` и пользовательский запрос.
2. Локализует узел в дереве AST по `id` секции или семантическому сходству.
3. Если активирован режим `enable_track_changes`:
   * Сохраняет старый вариант блока.
   * Создает новый вариант блока.
   * Помечает удаленные элементы тегами ревизий с указанием метаданных:
     - `author`: "AI Agent"
     - `date`: текущий ISO 8601 таймстемп
     - `type`: "insert" | "delete" | "replace"
4. Передает дифференциальный патч в модуль компилятора `revision_engine.py`.

## 6. Протоколы валидации и восстановление после сбоев

### Валидация JSON AST (Fail-Safe Loop)
Если языковая модель отдала невалидный JSON или нарушила схему:
1. Ошибка перехватывается Pydantic ValidationError.
2. Текст ошибки и исходный ответ отправляются агенту-корректору (`AST Repair Prompt`):
   ```
   Исходный JSON вызвал ошибку валидации схемы:
   {pydantic_error_details}
   Исправь структуру JSON, сохранив исходный смысл, и верни только валидный JSON.
   ```
3. Максимальное количество попыток исправления: **2**. При превышении — аварийный откат секции к тексту по умолчанию с сохранением работоспособности всего документа.

### Валидация OpenXML компиляции
1. Ошибки парсинга LaTeX изолируются в конвертере: некорректная формула преобразуется в курсивный моноширинный текст, а в лог пишется `WARNING`.
2. Все таблицы проверяются на совпадение количества элементов строки с количеством заголовков. Недостающие ячейки дополняются пустыми строками во избежание сбоя сетки Word.
